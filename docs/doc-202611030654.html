一、业务场景（背景）

  1. 用户在代购系统提交包裹（提包单），按预估重量/体积支付预估运费；
  2. 仓库（集运系统）拣货、打包，打包完成后重新称重测量，得到实际重量/体积；
  3. 集运系统将实际重量/体积回传代购系统（现有能力）；
  4. 代购系统按实际数据重新计算运费，与已收运费比对，产生多退少补；
  5. 判定需要补款时，代购系统通知集运系统拦截该包裹（暂停发货）；用户补款完成后，通知取消拦截、继续发货。

分工原则：是否需要补款由代购系统判定；拦截动作由集运系统执行。集运系统不做费用判断，只接收并执行代购系统指令。

二、需要集运系统支持的业务点（核心）

编号业务点性质说明
1核重结果回传现有能力，复用打包核重完成后回传实际重量/体积（接口①，已具备，确认字段完整性即可）
2接收并执行拦截 / 取消拦截指令新增（必须）收到拦截指令后包裹仓内留置；收到取消拦截后恢复正常（接口②③）
3发货前拦截确认建议新增包裹出库交接物流前，向代购系统确认该提包单是否可发货，确认通过才出库（接口⑤，详见第五节）
4已发货状态通知现有能力，复用提包单发货后通知代购系统（接口④，已具备）
5重赋快递单号 + 无主件识别入库场景需要用于「用户拒补换线路」人工兜底流程（见第七节）

以上为代购系统侧提出的业务诉求与建议，具体实现方式由集运团队自行评估设计。集运侧新增开发集中在业务点 2（拦截/取消拦截指令），其余均为现有能力复用或建议项。

四、接口调用场景

仅描述调用场景与数据要求：什么时机、谁调谁、携带什么、期望什么结果。技术形式（API / 消息等）由两系统技术对接时确定。

接口① 核重结果回传（集运系统 → 代购系统）【现有能力，复用】

  • 时机：包裹打包、核重测量完成后实时回传；
  • 数据：提包单号、包裹编号、实际重量、实际体积（长宽高）、核重时间；
  • 代购侧处理：触发运费重算与差额判定；应答接收结果（成功/失败），失败支持重推；二次核重时再次回传，以最新一次为准；
  • 说明：该接口已具备，对接时确认字段完整性与回传时机即可。

接口② 核重处理结果指令（代购系统 → 集运系统）【新增，必须】

  • 时机：代购系统完成重算判定后实时下发；
  • 指令类型：
    • 放行：正常流转、发货；
    • 拦截：暂停发货、包裹仓内留置；附拦截原因（待补运费）、补款单号、补款金额；
  • 说明：集运系统不单独应答执行结果。

接口③ 取消拦截指令（代购系统 → 集运系统）【新增，必须】

  • 时机：用户补款到账确认后实时下发；
  • 数据：提包单号、补款单号、补款金额、到账时间；
  • 期望：解除拦截，包裹恢复正常发货流转。

接口④ 提包单状态通知（集运系统 → 代购系统）【现有能力，复用】

  • 时机：提包单状态变更时通知代购系统；
  • 必须覆盖：已发货——代购系统据此同步提包状态；
  • 可选：已核重 / 已拦截 / 已解除拦截 / 已退回等状态，是否回传由集运自行决定，代购系统不强制；
  • 数据：提包单号、变更后状态、变更时间；
  • 说明：该接口已具备，直接使用。

接口⑤ 发货前拦截确认（集运系统 → 代购系统）【建议新增】

  • 时机：包裹出库发货前（交接物流前的最后关口），对待发货包裹发起确认；
  • 数据：提包单号；
  • 代购返回：可发货 / 不可发货（拦截中，原因：待补款）；
  • 期望：返回「不可发货」时包裹禁止出库；返回「可发货」时正常交接物流。

五、发货前拦截确认（建议）

代购系统建议：集运系统在包裹出库发货前（交接物流前的最后关口），对待发货包裹向代购系统发起确认（接口⑤），确认「可发货」才交接物流。

原因与价值：

  • 拦截指令是异步下发的，仅靠指令存在时间窗口（核重回传→代购判定→拦截指令到达期间，包裹可能已流转发货）；
  • 发货前确认把拦截生效点收敛到出库前最后一刻，可彻底避免「待补款包裹被误发」。

实现形式（供参考，由集运团队自行决定）：

  • 实时确认：出库前调用接口⑤，按返回结果执行；
  • 本地标识校验：依据已收到的拦截指令在本地维护拦截标识，发货前强制校验。

接口异常处理建议：确认接口超时/失败时，建议默认不放行或有限重试后转人工确认，避免「确认失败=放行」的漏洞；具体策略技术对接时确定。

六、代购系统侧处理（背景参考）

以下为代购系统内部处理逻辑，供集运团队理解全貌，不需要集运系统配合改造。

6.1 状态模型（不新增提包状态）

代购系统不新增任何提包状态枚举，用现有字段组合表达全流程：

场景提包状态补款状态
判定无差额 / 多退待发货无需补款
判定少补（拦截中）待发货（卡住不动）待补款
补款到账待发货已补款
正常发货已发货无需补款 / 已补款
拦截失败（异常）已发货待补款
拒补换线（人工关闭）已取消—（补款单作废）

注：若因误操作导致待补款包裹被发货（提包状态「已发货」+ 补款状态「待补款」），代购系统内部走人工追偿与用户风控，无需集运系统配合。

6.2 补款判定规则（按续重单位）

  • 补款以一个续重单位为最小粒度：实际重量增量不足一个续重单位 → 不补款、直接放行；
  • 增量 ≥ 1 个续重单位 → 按超出档数补款（金额 = 超出档数 × 续重单价），不存在小额零星补款。

6.3 资金联动

场景用户侧租户侧（运费基准成本）
下单支付收取预估运费按预估运费扣除租户基准成本
多退差额退至用户余额基准成本按差额退回租户
少补用户支付补款补款到账后基准成本差额补扣租户
拒补换线（人工关闭）预估运费全额退余额基准成本全额退回租户
拦截失败已发货补款单保留，人工追款追回后按少补规则入账

6.4 补款单规则

  • 补款无有效期，待补款提包单不自动取消，用户侧只有「补款」一个动作；
  • 用户长期不补 → 客服线下联系；
  • 用户拒补要求换线路 → 人工兜底流程（第七节）。

七、特殊场景：用户拒补换线路（人工兜底）

7.1 触发场景

提包单已核重、判定需补款（拦截中），用户不愿补款，希望换一条物流线路重新发货。由客服发起，全程人工处理，两系统不新增接口。

7.2 流程与分工

用户拒补申请换线
  → 集运系统：已打包包裹重赋新快递单号 → 无主件识别重新入库
  → 代购系统：后台手动创建订单、关联新快递单号（包裹归属用户，已入库）
  → 代购系统：原提包单关闭（→已取消）+ 预估运费全额退余额 + 补款单作废 + 原代购订单手动完成
  → 用户针对已入库包裹重新发起提包单（选新线路，重新支付预估运费）
步骤代购系统集运系统
包裹重赋单号—✔ 已打包包裹赋予新快递单号
无主件识别入库✔ 接收识别结果✔ 按无主件流程处理入库
手动建单关联✔ 后台手动创建订单并关联新单号—
原单收尾✔ 提包单关闭退款、补款单作废、代购订单手动完成—
新提包单✔ 用户重新发起提包（新线路）✔ 正常打包发货流程

说明：全程复用已有无主件识别与包裹入库能力；人工操作须留完整日志；新提包单与原提包单互不影响。
