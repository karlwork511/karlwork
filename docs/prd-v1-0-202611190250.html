一、需求背景

1.1 现状

运营中心 → 消息触达 当前只有「发送记录」一个页签，只能查看历史发送结果，既无法管理消息模板，也无法主动发起定向发送。

实际运营中存在三个具体问题：

1. 文案散落在代码里：43 个业务节点的用户通知文案写在各业务模块内部，改一句话要走一次发版，运营无法自助调整。 2. 渠道没有统一开关：站内信、邮件、PUSH 三个渠道缺少按场景的独立开关，部分场景只应发站内信却同时触发了邮件，造成用户打扰。 3. 海外用户只能收到中文：平台面向多个语种市场，现有通知只有中文，海外用户需要人工翻译后手工发送，时效和准确度都不可控。

1.2 目标

把「消息触达」从"发送记录查看"升级为「模板管理 + 主动发送 + 记录回溯」的完整闭环：

  • 43 个业务场景的通知模板统一在后台维护，运营可自助改文案、开关渠道
  • 一份模板覆盖五种语言，自动翻译 + 人工校正
  • 运营可自主发起定向发送，不再依赖开发介入

1.3 衡量指标

指标目标
模板覆盖率43 个场景 100% 有可用模板
多语言覆盖五个语种的模板可用率
运营自主率主动发送请求无需开发介入的比例
触达准确率发送失败率（渠道超限、变量缺失）下降

三、信息架构

运营中心
└─ 消息触达
   ├─ 消息发送    运营手动发起，选渠道、写内容、选人群、定时间
   ├─ 消息模板    43 个业务场景的自动触发模板管理
   └─ 发送记录    历史发送结果查询（本期沿用现有）

三个页签的分工边界：

  • 消息模板：业务事件自动触发，渠道由模板开关决定
  • 消息发送：运营手动发起，渠道由运营当次选择
  • 发送记录：两者的结果都汇总在这里

七、多语言规则

7.1 支持语言

语言说明
中文简体源语言，默认页签
中文繁体由中文简体翻译生成
English由中文简体翻译生成
日本語由中文简体翻译生成
Русский由中文简体翻译生成

7.2 存储规则

每个场景、每个渠道、每种语言独立存储一份标题和正文。即：43 个场景 × 3 个渠道 × 5 种语言。

7.3 翻译规则

规则说明
源语言中文简体为唯一源语言，必须填写
翻译方式点击一键翻译，调用翻译接口批量生成其余四种语言
人工校正翻译结果可逐条修改，修改后以人工版本为准
未翻译标记未翻译的语言在页签上显示红点
翻译覆盖一键翻译不覆盖已有的人工翻译内容，只补缺失的语言
发送回退发送时按客户语言偏好匹配，缺失则回退中文简体

7.4 翻译接口

调用 CMS 提供的外部翻译接口，返回结果直接写入对应语言模板。

八、变量规则

8.1 变量格式

变量用花括号包裹，例如 {order_number}。

8.2 白名单机制

每个场景绑定一组专属可用变量，编辑时只能插入白名单内的变量，不允许跨场景引用。例如订单类场景不能使用包裹类变量。

8.3 渲染规则

场景处理方式
预览按示例值渲染
发送替换为实际业务数据
变量为空显示为空字符串，不展示原始变量名

8.4 长度计算

PUSH 渠道下，变量按 8 字符计入长度校验，避免实际渲染后超限。
