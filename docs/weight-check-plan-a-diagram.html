代购系统 × 集运系统 核重补差对接说明（方案一）

用户支付预估运费后，仓库打包核重，代购系统重算运费、多退少补，需补款时指令拦截发货，建议发货前拦截确认收口

指令拦截 + 发货前确认 判定与资金 在代购系统 仓内执行 在集运系统 集运系统 不做费用判断，只执行指令

1两系统职责分工

代购系统

大脑：算钱、判定、收钱退钱、发指令

  • 下单时收取用户预估运费
  • 接收实际重量/体积，重算运费
  • 按续重单位判定：放行 / 多退 / 少补拦截
  • 退款：差额退用户余额，租户基准成本联动退回
  • 补款：生成补款单、通知用户、确认到账
  • 下发指令：拦截 / 放行 / 取消拦截
  • 应答发货前拦截确认（可发货 / 拦截中）
对接

集运系统（仓库 / WMS）

手脚：打包、称重、拦包裹、回传状态

  • 拣货、打包、核重测量（实际重量/体积）
  • 打包完成后实时回传核重结果（现有能力）
  • 执行拦截：被拦截包裹仓内禁止出库（新增）
  • 执行取消拦截，恢复正常发货（新增）
  • 发货后及时通知代购系统（已发货 · 现有能力）
  • 建议：发货前拦截确认，确认可发货才交接物流
  • 换线兜底：重赋快递单号、无主件识别入库

2核心交互时序（主干流程）

3三种判定结果 · 后续指令交互

A · 无需补差

无差额，或实际重量增量不足一个续重单位

代购系统判定：计费结果不变，不触发补款（补款状态：无需补款）
代购→集运② 处理结果指令：放行
集运正常流转，发货

用户全程无感知。

B · 多退

实际运费 ＜ 已收预估运费

代购系统判定多退，差额退至用户余额（补款状态：无需补款）
资金联动：租户运费基准成本按差额同步退回
代购→集运② 处理结果指令：放行
集运正常流转，发货

用户收到退款到账通知，无需任何操作。

C · 少补（拦截）

增量 ≥ 1 个续重单位，实际运费 ＞ 已收运费

生成补款单（金额 = 超出档数 × 续重价）
代购→集运② 处理结果指令：拦截（先拦截，再通知）
集运包裹留置暂停发货；提包单保持「待发货 + 待补款」
用户收到补款通知，完成补款
确认到账，补款状态→已补款，补扣租户基准成本差额
代购→集运③ 取消拦截指令
集运解除拦截，恢复发货

C2 长期不补：无有效期、不自动取消，客服线下联系

C3 拒补换线：走人工兜底流程（见第 7 节）

C4 误发兜底：待补款包裹被误发（已发货+待补款）→ 代购内部人工追偿，无需集运配合

4两系统接口清单（调用场景）

技术形式（API / 消息等）由两系统技术对接时确定；打包任务下发为已有能力，不重复列出。①④ 为现有能力直接复用；集运侧新增开发仅 ②③，⑤ 为建议新增。
编号 接口 方向 调用时机 关键数据 结果识别
① 核重结果回传现有 · 复用 集运 → 代购 打包、核重测量完成后实时回传 提包单号、包裹编号、实际重量、实际体积（长宽高）、核重时间 代购应答接收成功/失败，失败重推；二次核重以最新一次为准
② 处理结果指令新增 · 必须 代购 → 集运 运费重算与差额判定完成后实时下发 放行；或拦截：提包单号、补款单号、补款金额、拦截原因（待补运费） 集运不单独应答执行结果
③ 取消拦截指令新增 · 必须 代购 → 集运 用户补款到账确认后实时下发 提包单号、补款单号、补款金额、到账时间 解除拦截后包裹恢复正常发货流转
④ 提包单状态通知现有 · 复用 集运 → 代购 提包单状态变更时通知；「已发货」必须通知，其余状态按需 提包单号、变更后状态、变更时间 代购同步提包状态；支持主动查询补偿、定期对账
⑤ 发货前拦截确认建议新增 集运 → 代购 包裹出库发货前（交接物流前最后关口）发起确认 提包单号 代购返回可发货 / 不可发货（拦截中·待补款）；不可发货则禁止出库

统一要求：指令带唯一编号、可追踪可重发；同一指令重复下发幂等处理；以集运系统回传状态为准，定期对账保证两侧状态一致。

5发货前拦截确认（核心建议）

出库前最后关口确认，彻底避免待补款包裹误发

拦截指令是异步下发的，仅靠指令存在时间窗口（核重回传 → 代购判定 → 拦截指令到达期间，包裹可能已流转发货）。建议集运系统在包裹出库发货前向代购系统发起确认（接口⑤），返回「拦截中（待补款）」则禁止出库——拦截生效点收敛到出库前最后一刻。

包裹出库发货前 → ⑤ 集运 → 代购：确认是否可发货 → 可发货 → 交接物流 拦截中（待补款）→ 禁止出库

实现形式由集运自行决定：实时确认（推荐），或本地拦截标识发货前强制校验。接口超时/失败时建议默认不放行或有限重试后转人工确认，避免「确认失败=放行」的漏洞。若仍发生误发（已发货 + 待补款），由代购系统内部走人工追偿，无需集运配合。

6资金联动规则

用户侧与租户侧（运费基准成本）的资金对应关系；本链路不涉及技术服务费。资金处理为代购系统内部逻辑，供参考。
场景 用户侧 租户侧（运费基准成本）
下单支付 收取预估运费 按预估运费扣除租户运费基准成本
多退 差额退至用户余额 已扣基准成本按差额退回租户
少补 用户支付补款 补款到账后，基准成本差额补扣租户
拒补换线（人工关闭） 已付预估运费全额退至余额 已扣基准成本全额退回租户
拦截失败已发货 补款单保留，人工追款 追回后按少补规则入账，补扣基准成本差额

7特殊场景：用户拒补换线路（人工兜底）

触发：提包单已核重判定需补款、处于「待发货 + 待补款」（拦截中），用户不愿补款，希望换一条物流线路重新发货。由客服发起，全程人工操作，两系统不新增接口。

用户 / 客服

拒补，申请换线

客服确认换线方案，通知仓库处理

集运系统

重赋新快递单号

已打包包裹赋予新的快递单号

集运系统

无主件识别入库

按无主件流程重新入库

代购系统

手动建单关联

后台手动创建订单，关联新单号，包裹归属用户（已入库）

代购系统

原单收尾

原提包单关闭（提包状态→已取消）+全额退款、补款单作废、原代购订单手动完成

用户

重新发起提包

对已入库包裹选新线路，重新支付预估运费，走正常流程

说明：全程复用已有无主件识别与包裹入库能力；人工操作须留完整日志（谁关闭、谁退款、谁建单、谁关联）；新提包单与原提包单互不影响。

8方案一 vs 方案二

两方案独立可选，解决同一业务问题（核重多退少补、少补拦截发货）。方案二详见《代购集运_核重补差系统交互方案二》。
维度 方案一（指令拦截 · 本方案） 方案二（支付控制）
拦截抓手 新增拦截/取消拦截指令，建议发货前确认 利用集运单「未支付不发货」现状，天然拦截
集运侧改造 新增接口②③（必须）+ ⑤（建议） 零新增开发，①④与支付接口全为现有能力
代购侧改造 拦截指令下发、状态监听 台湾开关、收货地址识别、调支付接口
台湾/中国件 与其他线路一致走拦截 放弃少补（开关控制），只多退
拦截可靠性 异步指令有时间窗口，靠发货前确认收口 天然拦截，无时间窗口
发货时效 无额外环节 所有国际件发货前多一步支付接口调用
长期不补款 包裹拦截压仓，客服线下联系 集运单未支付压仓（集运无自动处理规则），客服线下联系
拒补换线 重赋单号 + 无主件 + 原单关闭 同上，另需手动作废原集运单（集运现有流程）
