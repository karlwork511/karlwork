核重补差交互方案（方案二：支付控制）

POKO SaaS

代购系统 × 集运系统 核重补差交互方案二 v1.0

版本：v1.0（2026-11-03） 定位：面向集运系统团队的对接沟通文档。方案二与方案一解决同一业务问题（核重多退少补、少补拦截发货），是另一种实现路径：利用集运系统现有「集运单未支付不发货」机制实现天然拦截，集运侧零新增开发。 与方案一的关系：两方案独立可选，对比见第七节。

一、核心思路

方案一靠「新增拦截指令」让集运系统主动拦包裹；方案二不新增任何拦截能力，改用集运单支付控制作为拦截抓手，基于集运系统两个现状：

  1. 国际件集运单默认「未支付」：打完包后需支付集运单才发货——代购系统不调支付接口，包裹就天然发不出去，这就是拦截；
  2. 台湾线路不触发拦截：收货地址为台湾/中国的件，集运系统现状没有拦截抓手——方案二对此类件放弃少补（只多退），由代购系统 SAAS 平台端开关控制。

集运侧改造量：零新增开发。核重回传、已发货通知、集运单支付接口均为现有能力。

二、分线路处理规则（核心）

代购系统收到核重结果后，先识别收货地址，再按线路走不同规则：

收货地址多退少补拦截方式
台湾 / 中国正常退差额至用户余额放弃补款：不变更补款状态，仅记录核实重量/体积，包裹正常流转发货（无金额上限）不拦截（集运现状不支持）
其他国家正常退差额，判定后调集运单支付接口放行生成补款单，集运单保持未支付（天然拦截）；用户补款到账后，代购调集运单支付接口完成支付，放行发货集运单未支付天然拦截

台湾地区不进行补款开关：

  • 代购系统在 SAAS 平台端新增平台级总开关「台湾地区不进行补款」；
  • 开启时（当前业务决策）：台湾/中国件少补直接放弃；
  • 关闭时：台湾/中国件恢复补款判定逻辑——但集运台湾线路无拦截能力，补款拦截无法生效，需谨慎关闭。

四、接口调用场景

仅 3 个接口，全部为集运系统现有能力，无新增开发。

接口① 核重结果回传（集运系统 → 代购系统）【现有】

  • 时机：包裹打包、核重测量完成后实时回传；
  • 数据：提包单号、包裹编号、实际重量、实际体积（长宽高）、核重时间；
  • 代购侧处理：触发运费重算、识别收货地址、分线路判定；二次核重以最新一次为准。

接口② 集运单支付接口（代购系统 → 集运系统）【现有能力，新调用场景】

  • 时机（其他国家件）：
    • 判定无差额 / 多退 → 判定完成后直接调用，支付放行；
    • 判定少补 → 用户补款到账确认后调用；
  • 数据：集运单号 / 提包单号；
  • 期望：集运单置为已支付，集运系统安排发货；
  • 代购侧兜底：调用超时 / 失败时自动重试，多次失败告警转人工；补款已到账但支付未成功期间，提包单保持「待发货 + 已补款」，不流失。
  • 说明：集运单支付为平台与集运系统之间的结算确认动作；平台与集运之间的实际资金为线下结算，与系统交互无关。

接口④ 提包单状态通知（集运系统 → 代购系统）【现有】

  • 必须覆盖：已发货——代购系统据此同步提包状态；
  • 数据：提包单号、变更后状态、变更时间。

与方案一接口编号对应：①④ 同方案一；方案二不再需要方案一的拦截/取消拦截指令（②③）与发货前拦截确认（⑤），新增「集运单支付」调用场景。

五、代购系统侧处理（背景参考）

以下为代购系统内部处理逻辑，供集运团队理解全貌，不需要集运系统配合改造。

5.1 状态模型（不新增提包状态）

场景提包状态补款状态说明
台湾/中国件·少补正常流转（待发货→已发货）无需补款（不变更）提包单记录核实重量/体积
其他国家件·少补（拦截中）待发货（卡住不动）待补款集运单未支付天然拦截
其他国家件·补款到账待发货已补款调支付接口放行
正常发货已发货无需补款 / 已补款—
拒补换线（人工关闭）已取消—（补款单作废）见第六节

「放弃补款」单据的区分口径：补款状态保持「无需补款」，与真正无差额的单共存；可通过「核实重量 ＞ 预估重量 + 补款状态=无需补款 + 收货地址=台湾/中国」组合筛选，用于对账与亏损统计。

5.2 资金联动

场景用户侧租户侧（运费基准成本）平台 ↔︎ 集运
下单支付收取预估运费按预估运费扣除租户基准成本—
多退差额退至用户余额基准成本按差额退回租户按实际核重支付集运单
少补（其他国家件）用户补提包单运费差价补款到账后，从租户余额补扣基准成本差额补款到账后支付集运单
台湾/中国件·少补不补款基准成本按实际核重核算按实际核重支付集运单；少补差额不再向用户收取
拒补换线（人工关闭）预估运费全额退余额基准成本全额退回租户原集运单手动作废

5.3 补款单规则

  • 补款无有效期，待补款提包单不自动取消，用户侧只有「补款」一个动作；
  • 集运系统对超期未支付的集运单无自动处理规则（已确认），包裹长期压仓不构成系统异常，「无有效期」成立；
  • 用户长期不补 → 客服线下联系；拒补换线 → 人工兜底（第六节）。

六、特殊场景：用户拒补换线路（人工兜底）

与方案一一致，仅一处差异：

用户拒补申请换线
  → 集运系统：已打包包裹重赋新快递单号 → 无主件识别重新入库
  → 集运系统：原集运单（未支付状态）手动作废 ←—— 方案二新增步骤，集运现有流程
  → 代购系统：后台手动创建订单、关联新快递单号
  → 代购系统：原提包单关闭（→已取消）+ 全额退款 + 补款单作废 + 原代购订单手动完成
  → 用户针对已入库包裹重新发起提包单

七、方案一 vs 方案二对比

维度方案一（指令拦截）方案二（支付控制）
拦截抓手新增拦截/取消拦截指令，建议发货前确认利用集运单「未支付不发货」现状，天然拦截
集运侧改造新增接口②③（必须）+ ⑤（建议）零新增开发，①④与支付接口全为现有能力
代购侧改造拦截指令下发、状态监听台湾开关、收货地址识别、调支付接口
台湾/中国件与其他线路一致走拦截放弃少补（开关控制），只多退
拦截可靠性异步指令有时间窗口，靠发货前确认收口天然拦截，无时间窗口
发货时效无额外环节所有国际件发货前多一步支付接口调用
长期不补款包裹拦截压仓，客服线下联系集运单未支付压仓（集运无自动处理规则），客服线下联系
拒补换线重赋单号+无主件+原单关闭同上，另需手动作废原集运单（集运现有流程）

八、边界说明

  • 本文覆盖：方案二下代购系统的业务背景、对集运系统的接口调用场景（全部现有能力）；
  • 集运单支付的触发与异常重试为代购系统内部实现；平台与集运之间的资金结算走线下，与系统交互无关；
  • 代购系统内部实现（开关、地址识别、状态、资金、后台页面）仅作背景参考，不要求集运系统配合。
